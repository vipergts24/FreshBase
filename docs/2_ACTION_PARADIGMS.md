# Semantic Action Paradigms

## What Does It Mean to Revert?

In standard Git, a commit is a text delta. If Feature 2 (F2) is committed, and Feature 3 (F3) later modifies the same lines (or depends on them computationally), reverting F2 purely triggers a text merge conflict. A human has to fix the compilation error. 

**FreshBase introduces Semantic Versioning.** A commit is no longer just text; it is `{ Intent, Specification, Code, Tests }`.

### The Scenario
1.  **Feature 1:** Set up Auth.
2.  **Feature 2:** Add a customized Data Table component on the dashboard.
3.  **Feature 3:** Add an Export-to-CSV button on the dashboard.

*The Code Reality:* F3's code imports utility properties from F2's Data Table implementation to gather the data for CSV export.
*The Intent Reality:* F3's goal is "Export user dashboard data", which fundamentally *doesn't* require the Data Table UI to exist, only the data itself.

### Goal-Oriented vs. Code-Oriented Dependencies

If the Director decides: **"Revert Feature 2 - the Data Table is too distracting right now."**

1.  **Dependency Graph Calculation:** FreshBase analyzes the graph. F3 *code-depends* on F2. However, F3 does not *goal-depend* on F2.
2.  **The Sub-Swarm Trigger:** Instead of flagging a textual merge conflict for a human to fix, FreshBase triggers a "Resolution Swarm".
3.  **The Resolution:** 
    *   The Agent is instructed: "Keep Feature 1 and Feature 3's Intents intact. F2 has been reverted. Feature 3 is currently failing tests because it relied on `dataTable.utils.js`. Re-write Feature 3 so it fetches the data directly from the API layer without relying on F2."
4.  **The Result:** F2 is removed. F3 is automatically refactored in a shadow branch, verified against F3's original tests, and merged. 

We have fundamentally shifted from "Revert Patch" to **"Re-Synthesize Codebase sans-Intent #2"**.

## Taming LLM Unpredictability

You flagged a critical risk: If two agents cause a true logic conflict, and an LLM attempts to synthesize the merge automatically, it might hallucinate code that passes a syntax check but structurally betrays the business logic.

How does FreshBase solve this?

### The Triangle of Trust
An LLM is never allowed to modify source files directly without a counterbalance.

1.  **The Intent (Natural Language)**: "I want the API to rate limit at 100 req/sec."
2.  **The Verification (Deterministic Code)**: `test_rate_limit_enforced()` written in PyTest/Jest *before* implementation.
3.  **The Implementation (Probabilistic Code)**: The actual code patch generated by the LLM.

### Merge Conflict Protocol
When a conflict arises, an LLM never "just synthesizes a patch". 

Instead:
1.  All deterministic tests from branch A and branch B are pulled into the conflict arena.
2.  The Resolution Agent is tasked to write code that passes **100% of both test suites simultaneously.**
3.  If the tests inherently contradict (e.g., test A requires exactly 10 items, but test B requires exactly 0 items), the system mathematically identifies the logical paradox.
4.  It is *only* at this point of logical paradox that the Human Director receives a ping: *"Feature A and Feature B are structurally incompatible. Please clarify intent."*

By forcing the system through the deterministic bottleneck of TDD (Test Driven Development), we insulate the codebase from hallucinated logic drift.
